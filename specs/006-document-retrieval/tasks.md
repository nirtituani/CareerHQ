      same object cannot see the difference. The persisted half commits *after* the refusal and

      nothing. **The rule is now inverted.** Every mention of the class in a permitted module is
      classified against a whitelist — construction, column reference, `select(...)`, type
      annotation — and **anything else fails**, including handing it to a function whose body the
      gate never reads. This is the one place a drill changed the design rather than confirming it.

      **Why pre-deploy, and why the alternatives were rejected:**
      - **Once per deploy, not once per replica. This is why the startup hook is ruled out.** A
        startup hook pays the model load on every container start, delaying readiness — and two
        replicas booting together race on `uq_knowledge_chunks_document_content`, turning a

        ingestion. Pre-deploy has neither problem.

        exist before anything writes to it.

        the database, and the files and the database would disagree about what guidance exists —
        exactly the drift `content_hash` exists to detect, arriving by process rather than by bug.

- [ ] **T051** **Role context in the exported résumé — employer, job title and dates.**
      *(Appended 2026-08-28 at T036. Design not decided; not started.)*
      `ResumeDocument` carries a name, a contact line and ordered sections of text. It carries **no
      employer, job title or date for any role**, so an exported résumé lists experience bullets
      with nothing saying where or when — and the corpus's own ATS rule, sourced to a vendor,
      requires the opposite: *"Give each role an explicit employer name and job title as separate
      readable text rather than combining them into one styled line. Current title and current
      employer are extracted as distinct fields."*
      **Why it is not T031/T034/T036's.** T031 built the smallest model its assertions needed;
      T034 owns the template, not the content; T036 is persistence and lifecycle, and FR-017
      defines the exported text as *"the approved items and their approved order"* — which is what
      it exports. Fabricating role context inside the exporter was explicitly refused.
      **What it needs, and why it is a decision rather than a field.** The information lives on
      `WorkExperience` in the profile, not on `ResumeVersionItem`, so the export would have to load
      profile context and nest bullets under roles — changing `ResumeDocument` from a flat section
      list to a nested one. That raises a question this slice has not answered: a version
      snapshots its items so a later profile edit cannot change it (Principle IV), so **role
      context read live from the profile would not be snapshotted**, and an approved document could
      change underneath its own checksum. Either the version carries the role context too, or the
      export accepts that part of the document is not snapshotted.
      **Do not implement before that is decided.**

- [ ] **T052** **The token ceiling budgets rule text; the prompt carries citations too.**
      *(Appended 2026-08-29 at T046, from T045's measurement. Design not decided; not started.)*
      **This is why SC-008 is missed**, and it is an accounting discrepancy rather than a
      retrieval defect. `KnowledgeChunk.token_count` counts the **rule text**, and
      `_retrieve`'s budget is spent against it — but `prompts.py::_guidelines` renders
      `- {text}  [{source}]`, and `source` is `document_slug · locator · content_hash` per
      guideline. Measured on the real prompt builder: the static block is **492 tokens** (358
      text + 134 citations) and the retrieval block is **2,190** (1,523 + **667**). A ceiling
      configured at 1,500 therefore reaches the model at ~2,190 — **46% over** — and the
      uncounted third is what puts SC-008 at 2.12% instead of the ~1.5% the spec predicted.
      **The ceiling is doing exactly what it says. What it says is narrower than what is sent.**
      **Four options, none of them free, and none chosen here:**
      1. **Count the rendered form.** Budget `len(text) + len(citation)` so 1,500 means 1,500 at
         the model. Honest, and it *reduces the guidance* — roughly a third fewer rules for the
         same ceiling, which is a retrieval-quality change, not a bookkeeping one.
      2. **Shorten the citation.** `content_hash` is rendered at 12 characters already; the slug
         and locator are what a person reads. **FR-012 needs the citation to be resolvable**, and
         T028 snapshots the full identity in `guidelines_used` *separately from the prompt* — so
         the prompt's copy could in principle be shorter than the snapshot's. That is a real
         option and a real risk: the two would no longer be the same string.
      3. **Raise the ceiling to match reality** and accept SC-008 as missed. Changes nothing
         about cost; only stops the number being surprising.
      4. **Accept it.** SC-008 stays missed at 2.12%, recorded, with the cause measured.
      **Do not pick one to make a threshold pass.** Options 1 and 2 both trade retrieval quality
      or citation integrity for 0.12 percentage points, and FR-012's resolvability and T028's
      snapshot are load-bearing. **The measurement is the deliverable; the fix is a decision.**

- [ ] **T053** **The configured embedding model is not the one baked into the image.**
      *(Appended 2026-08-29 at T046, from T044's measurement. Not started.)*
      `config.py` defaults to `BAAI/bge-small-en-v1.5` and the Dockerfile bakes **only** that —
      verified: the image's `/app/.model-cache` contains `bge-small` alone. But `.env` **and
      `.env.example`** set `EMBEDDING_MODEL=sentence-transformers/all-MiniLM-L6-v2`, so the model
      actually used is **downloaded from Hugging Face at first warm-up**. That contradicts D3's
      *"no network call in the retrieval path"* and the Dockerfile's own comment, *"so a cold
      container never downloads from Hugging Face"*.
      **The mismatch is silent by construction.** Both models are 384-dimension, so
      `EMBEDDING_DIMENSIONS` cannot catch it. Ingesting with one and querying with the other
      returns confident nonsense and nothing raises. Today they agree — T050 ingested with MiniLM
      and T044 measured with MiniLM — but **changing either side alone breaks retrieval
      invisibly**, and the two sides live in different files that nobody edits together.
      **Fixing it means choosing one model**, which is a deployment decision (image size, cold
      start, retrieval quality) and belongs with **T048**. A guard that fails loudly when the
      ingested corpus and the query embedder disagree would be worth more than the choice itself.

- [ ] **T054** **The tailor screen offers dead controls on a locked version, fails silently, and
      hides the one action it tells you to take.**
      *(Appended 2026-08-29 at T047, found in the browser. Three related frontend defects on one
      screen. Not started — T047 is verification and owns no fix.)*
      **All three are frontend-only. The backend is correct throughout**: it refuses with 409 and
      the exact T039 message, the item does not change, and the submission is untouched. Nothing
      about data integrity is at stake — what is at stake is a person believing they changed a
      résumé they did not.
      1. **Dead affordances.** `Accept` / `Reject` / `Edit` render on `exported` **and**
         `submitted` versions, where T039 guarantees every click is a 409. `approved` is computed
         as `ready || exported || submitted` and gates the export controls; the item rows are not
         gated at all.
      2. **The refusal is silent.** `decide()` in `tailor-tab.tsx` has **no `catch`** — the
         rejected promise goes nowhere and the screen does not move. `exportPdf` and
         `markSubmitted` both `catch → setError`. **This is the defect T037 fixed for the export
         path, on the one path that never got it**, and its own words apply unchanged: *"silence
         after a click reads as success."* Reproduced in the browser: clicked Reject on a
         submitted résumé, nothing appeared, `data-testid="tailor-error"` was absent, and the API
         had answered **409**.
      3. **The action the screen instructs is not offered.** The submitted view says *"tailor this
         job again — that produces a new version and leaves this one as it was sent"*, and the
         only controls on the page are Download PDF and the three dead ones. **FR-025 works and is
         tested (T041); through the UI it is unreachable.**
      **Why the suite missed all three.** `tailor.test.tsx` asserts the *export and submit*
      controls are absent for a submitted version, and asserts an error renders for a failed
      **export** and a failed **submit** — never for a failed item decision, and never that the
      decision buttons are gone. The frontend tests and the backend tests were each right about
      their own half. This is the project's own rule holding again: **the suite has never once
      caught a display bug.**
      **Do not fix inside a verification task.** Gating the rows is one line; the error handling is
      three; the revision affordance is a product decision about what the submitted view should
      offer, and it is the one that actually matters.

- [ ] **T055** **CI renders with different system libraries and a different font than production.**
      *(Appended 2026-08-29 while fixing FR-031. Not started — deliberately out of that fix's
      scope, which changed no CI or Docker configuration.)*
      `.github/workflows/ci.yml` installs **no system packages at all** — its only step is
      `pip install -e ".[dev]"`. WeasyPrint therefore binds whatever Pango, Cairo and
      fontconfig `ubuntu-latest` happens to ship, and resolves whatever fonts happen to be
      on the runner. **`backend/Dockerfile` declares `fonts-dejavu-core`, `libpango-1.0-0`,
      `libpangoft2-1.0-0` and `libcairo2` explicitly**, and T032 recorded why: *"which font
      resolves decides the rendered bytes"* — measured at the time as an 8,885-byte document
      becoming 11,499 when the family changed.
      **So the six ATS assertions and the byte-determinism assertion are green against a
      document production does not produce.** They still test real properties — single
      column, no tables, character integrity — but not against the bytes an employer would
      receive. A base image change on the runner could alter CI's output without touching
      anything this repository declares, which is the exact failure mode the Dockerfile's
      declaration was added to prevent, left open in the environment that does the asserting.
      **Three options, none chosen here:** install the same packages in CI so the two agree;
      run the backend job **in the built image** so there is one environment rather than two;
      or state explicitly that CI checks renderer-independent properties only and move the
      font-sensitive assertions somewhere that uses the real image. The second is the only
      one that cannot drift.
      **Not a blocker for FR-031**, which is now satisfied on every runtime — the timestamp
      pin is environment-independent.
