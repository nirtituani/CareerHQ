# How much technical detail a role wants

**Authored, `trust_level: internal`, `origin_source_ids` deliberately empty.** The source register
records this as a **gap**: no source in it addresses role-specific technical depth, and the shipped
rubric has no rule on it either. These are therefore CareerHQ product judgement, labelled as such,
rather than guidance derived from evidence that does not exist.

**No per-role-family files accompany this one.** Authoring separate backend, data, devops and
security documents would mean inventing role-specific claims with nothing behind them — the
decorative-citation problem the sample review caught, at six times the scale. They arrive when
there are sources to derive them from.

## Rules

- Move technical specificity up or down to match what the posting values. A posting written by
  engineers and dense with named systems wants the specific technologies and versions the profile
  records; one written for a general audience wants the problem solved and the outcome, with the
  technology present but not leading.

- Where the posting names a technology the profile also records, use the profile's own level of
  detail about it rather than expanding to match the posting's emphasis. A posting's prominence is
  a statement about the employer's needs, not evidence about the depth of the candidate's use.

- Where a role spans several disciplines and the posting concerns one, lead each bullet with the
  part that serves the posting and keep the rest brief. Removing the other disciplines entirely
  misrepresents the role's shape, which the candidate may be asked about.

- Where the profile describes work in the vocabulary of one discipline and the posting is in
  another, translate the vocabulary only where the underlying work genuinely maps. An analogy that
  reads well is still a claim about experience the candidate has not had.
